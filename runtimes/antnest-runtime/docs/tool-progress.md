# Tool Progress

This document defines how the Runtime produces live progress notifications for
built-in Bash and managed stdio MCP tool calls, including limits, the internal
executor framing, and failure semantics. ACP consumes these notifications and
owns `tool_call_update` persistence and presentation. Progress adds no Runtime
tables, durable queues, new endpoints, or per-packet telemetry.

## Scope And Contract

The caller supplies `_meta.progressToken` in `tools/call`. Runtime uses the
official SDK's `notifications/progress` on that request's Streamable HTTP
response. Without a token there are no progress notifications. Tokens belong
to the caller and active request only, not an Agent or a durable subscription.
See the [MCP progress contract](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/progress)
and the pinned `rmcp` model used by Runtime's `2026-07-28` transport.

1. Bash reports captured stdout/stderr increments as human-readable messages
   prefixed `stdout: ` or `stderr: `. `progress` counts emitted preview UTF-8 bytes;
   `total` is absent. It is not a percentage or a heartbeat. Per-stream byte
   order is preserved; no causal ordering between the two OS pipes is claimed.
2. UTF-8 sequences split across reads are retained until complete. Invalid
   bytes use replacement characters, consistently with the final Bash result.
   Final stdout/stderr remain authoritative and retain their 1 MiB per-stream
   bound. A silent command produces no invented progress.
3. Managed MCP progress is observed at the SDK-decoded transport boundary,
   before dispatch can return a result. Runtime subscribes before sending the
   child request, filters on its SDK-generated token, then rewrites only the
   token to the outer caller's token. Valid increasing progress, the optional
   total and bounded message text are preserved. Unrelated, late or
   non-increasing reports are ignored.
4. Progress is an optional, bounded live preview, not a reliable event journal.
   Each request has at most 32 queued reports, 8 KiB message text per report,
   and 256 forwarded reports. Queue overflow or the report limit ends previews
   with an explicit truncation notice when delivery is still possible. A slow
   or disconnected subscriber does not block execution indefinitely: each
   notification has a one-second send bound, with one payload-free warning on
   delivery failure. The final tool result is not replaced by a progress error.
   Final preview draining shares one additional one-second bound. Unrelated
   child tokens over 128 bytes are ignored before buffering; the child request
   tokens generated by Runtime's SDK are integers.
5. No progress may outlive the request. Runtime drains the bounded accepted
   preview tail before the final reply, stops on cancellation, and drops the
   receiver when the request ends. Progress never resets the tool's hard
   deadline. Cancellation keeps the existing current-invocation containment
   policy; previous background jobs and shared managed MCP processes are not
   killed.

## Internal Execution Boundary

The root Supervisor still executes no tool logic. Non-root same-binary tool
subcommands retain one input JSON and produce newline-delimited JSON on stdout:
zero or more `{"progress":{...}}` frames, then the existing single terminal
success/failure envelope. Non-Bash tools produce only the terminal frame.
The SDK never reads that private pipe directly. The Executor adapter bounds
frames and the aggregate response, rejects a missing or duplicate terminal
frame and any progress after it, and translates previews independently of
result decoding. Child stderr remains diagnostics, never an extra progress
protocol.

The execution-domain progress value does not depend on MCP types. The MCP
adapter owns token association, notification validation and delivery limits.
The managed catalog owns child token matching, not Agent, Session or ACP state.

No progress payload, command, stdout/stderr or per-chunk span is exported to
logs or OTLP. Existing execution identity fencing, result and error envelopes,
single-flight execution, background-job lifetime and OTLP request spans are
unchanged by progress.

## Tests

The tests cover incremental delivery before completion, silence without a
token, UTF-8 boundaries, bounded flooding and slow consumers, a single terminal
result, partial output followed by cancellation or failure, and no cross-call
token leakage. Managed tests use the official SDK codec and a real stdio
fixture; Linux tests cover the actual non-root Executor pipe. HTTP tests use the
production stateless MCP transport rather than checking a constructed
notification only.

- `runtimes/antnest-runtime/src/progress_tests.rs` covers message and report
  bounds, overload marking without blocking the producer, and executor framing:
  progress before the terminal envelope, and rejection of missing, duplicate
  and post-terminal frames.
- `tests/integration/antnest-runtime/managed_progress.rs` checks that managed
  progress is live, scoped to the caller's token, and drained before the result.
- `tests/integration/antnest-runtime/mcp_progress_transport.rs` uses an unread
  SDK transport to reach the one-second delivery deadline and checks that the
  execution result is preserved.
- `make e2e-tool-progress` runs the deployment profile described in
  [the ACP progress E2E](../../../tests/e2e/acp-progress/README.md). It covers
  ACP v1 and v2 through the Gateway against real Bash and a managed stdio MCP
  server, including early output, cancellation, replay and Jaeger trace
  ancestry. `make test-tool-progress-fixtures` runs its fixture tests without
  Docker.
